# services/progress

Blueprint §10 names Progress as one of Dashboard's formal dependencies. This is a **Goals + Check-ins + Roadmap Progress domain**: deterministic consistency scores and trend labels computed purely from `CheckIn` data (via the `CheckInsView` interface, satisfied by the real `CheckInService`), plus - for a single goal - deterministic roadmap-completion counts computed purely from that goal's own `Roadmap` milestone/action-step status (via the `RoadmapView` interface, satisfied by the real `RoadmapService`).

`RoadmapProgress` (total/completed milestones, total/completed action steps, a rounded step-completion percentage) is read directly from the Roadmap's own status fields, not replayed from Activity events - Roadmap's own state is the authoritative source of "what's completed," and Activity is a log of what happened, not a second copy of current state Progress would need to keep in sync. `GoalProgress.roadmap` is `null` when the goal has no roadmap yet.

Deliberately not built: any calendar/cadence-based streak tracking (no defined check-in frequency exists yet to measure against), any roadmap-progress aggregate across all of a user's goals (only asked for per-goal), and any AI-generated interpretation of the numbers - `computeTrend()`/`computeRoadmapProgress()`'s own comments document the exact (placeholder, for trend) or purely-factual (for roadmap progress) logic used instead.
