# ADR 0016: File-backed durable persistence

**Status:** Accepted

## Context

Every domain's data (users, goals, goal history, profiles, onboarding state, check-ins) lived only in `InMemory*Repository` instances - real, working data models behind real repository interfaces (ADR 0001's adapter pattern), but wiped on every server restart. The user asked for durable local persistence next, explicitly scoped: adapter-based, no domain rewrites, preserve existing service interfaces, a simple and testable local persistence layer - not a production database migration.

## Decision

- **A new `packages/persistence` package** holds exactly two functions used by every domain: `readJsonArray(filePath)` (returns `[]` on a missing file - a fresh data directory is a legitimate empty-start state, not an error) and `writeJsonArrayAtomic(filePath, items)` (creates the containing directory if needed, writes to a temp file, then renames over the target - so a crash mid-write can never leave a truncated or corrupt data file). No new dependency was added; both are built on Node's `fs`/`path` builtins only.
- **One `File*Repository` per existing repository interface** (`FileGoalRepository`, `FileGoalHistoryRepository`, `FileUserRepository`, `FileProfileRepository`, `FileOnboardingRepository`, `FileCheckInRepository`), added alongside - not replacing - each domain's existing `InMemory*Repository`. Each loads its full dataset from a JSON file once at construction and persists the full current dataset after every mutating call. Every filtering, sorting, and null-handling behavior was copied exactly from its `InMemory*` counterpart (verified field-by-field against a full inventory of all six interfaces before writing any code) - including two real inconsistencies across domains that were deliberately preserved rather than "fixed": `GoalRepository`/`GoalHistoryRepository` sort ascending (oldest-first) while `CheckInRepository` sorts descending (newest-first). No domain service (`GoalService`, `AuthService`, etc.) changed at all - they still depend on the same interfaces, satisfied by a different adapter.
- **A `FileAuthProvider`, discovered mid-implementation, not just `FileUserRepository`.** `UserRepository` only holds the public-ish `users` record (id/email/status); the actual password hash and session tokens live entirely inside `LocalAuthProvider`'s own in-memory maps, behind the separate `AuthProvider` interface (ADR 0004's credential boundary). Persisting only `UserRepository` would have meant accounts still existed after a restart but nobody could log back in - the single most severe form of "lost data" this milestone was meant to prevent. `FileAuthProvider` persists identities (email + password hash) the same way every other adapter does.
- **Sessions are deliberately not persisted.** They're short-lived (24h TTL) and re-authenticating after a real server restart is normal, expected behavior - not the kind of data loss this milestone is about. This is a scoping decision stated explicitly in code, the same honesty pattern used for every other deliberately-deferred piece in this project.
- **`createDefaultDependencies()` takes an optional `dataDir` parameter.** No `dataDir` (every existing test call site, unchanged) means fresh, isolated in-memory state exactly as before this ADR - no existing test needed to change. Real server startup (`apps/api/src/index.ts`) is the only caller that passes one, sourced from a new `DATA_DIR` env var (default `./data`, following the same `getEnv()` pattern already used for `API_PORT`/`API_CORS_ORIGIN`). One JSON file per domain (`goals.json`, `goal-history.json`, `users.json`, `auth-identities.json`, `profiles.json`, `onboarding.json`, `check-ins.json`), human-inspectable, in that single directory.
- **The data directory is gitignored** (`Apps/api/data/`) - it now holds real account credentials and user data, not source code.

## Consequences

- No domain service, route, or contract changed. This is purely a new adapter layer, wired in at exactly the extension point ADR 0001 anticipated ("when a database is chosen, a new repository implementation is added and wired in - the service does not change").
- Verified at three levels: unit tests for the shared `readJsonArray`/`writeJsonArrayAtomic` primitives; a "simulated restart" unit test per `File*Repository` (construct one instance, write data, construct a completely independent second instance pointed at the same file, confirm it sees the data with correct semantics); and one full integration test that builds a real Express server via `createServer(createDefaultDependencies(tempDir))`, signs up, creates a goal, records a check-in, discards that server object entirely, builds a second independent server from the same `tempDir`, and confirms login plus both records are readable through the real HTTP API - plus a companion test confirming a token issued before that point is correctly rejected after (proving sessions really aren't persisted, not silently working by accident).
- Beyond the automated suite, verified against a real, separately-started Node process: ran the actual `tsx src/index.ts` entrypoint pointed at a real temp `DATA_DIR`, seeded an account/goal/check-in via real `curl` requests, hard-killed the process (`taskkill`, not a graceful shutdown), started a brand-new process against the same directory, and confirmed via `curl` that login and both records worked identically - the actual scenario ("stop losing app data on server restart") proven against a real process boundary, not just an in-process object swap.
- Whole-file-rewrite-per-mutation is simple and correct for this project's current data volumes, but doesn't scale indefinitely - a real database is still the eventual answer Product Vision/Blueprint leave open (ADR 0001); this milestone doesn't change that trajectory, it just stops the current in-memory approach from losing data before that decision is made.
