# ADR 0020: Roadmap domain and AI adapter boundary

**Status:** Accepted

## Context

Blueprint §6's onboarding formally ends in an AI-generated "Create Plan" step, and Dashboard (§10) formally depends on Roadmap alongside Goals, Check-ins, and Progress - neither has existed until now. Every prior milestone (Onboarding, Dashboard, Check-ins, Progress) was deliberately scoped short of its AI-dependent pieces, leaving onboarding's terminal step named `awaiting_roadmap` specifically anticipating this.

The user is separately building and validating Better You's actual AI model in a different project, outside this repository, before plugging it in here. That means this milestone must build the *product* side of Roadmap - the data model, validation, persistence, and lifecycle Better You itself owns - without building or depending on a real AI provider. It must also establish the seam the external AI project will eventually plug into, so that integration is additive later rather than invasive.

## Decision

- **A new `services/roadmap` domain**, structured identically to every other domain in this project (ADR 0001's adapter pattern): `Roadmap` → `Milestone` → `ActionStep` contracts in `packages/contracts/src/roadmap.ts`, a `RoadmapRepository` interface with `InMemoryRoadmapRepository`/`FileRoadmapRepository` implementations (ADR 0016 pattern), a `GoalLookup` structural interface (same shape as Check-ins'/Onboarding's), and a `RoadmapService` that owns creation, retrieval, and status transitions.
- **A `RoadmapGenerator` adapter interface** - `generateRoadmap(input: RoadmapGenerationInput): Promise<RoadmapDraft>` - is the only seam through which roadmap *content* enters the system. The only implementation today is `PlaceholderRoadmapGenerator`: deterministic, rule-based, no AI provider or API key, producing a fixed three-phase structure (get started / build consistency / reach the goal) from a goal's title alone. The external AI project referenced above will later plug in by implementing this same interface; no product-side code changes when that happens.
- **"AI proposes, Better You validates and persists," enforced in code, not just documentation.** Whatever a `RoadmapGenerator` returns - the placeholder today, a real AI model later - is treated as untrusted draft data and always passes through `validateRoadmapDraft()` before `RoadmapService` turns it into a persisted `Roadmap` with real ids and status. A generator has no access to Goals, Profile, or any other Better You state beyond the `RoadmapGenerationInput` it's handed; it cannot mutate anything directly. `validateRoadmapDraft()` takes `unknown`, not a typed `RoadmapDraft` - every field (including nested milestones/action steps) is type-checked explicitly at runtime before use, so a generator returning a malformed shape (e.g. a numeric `title`) fails with a `RoadmapValidationError` instead of a raw `TypeError`/500 from code like `.trim()` on a non-string. A real AI model's output cannot be assumed to match the TypeScript interface just because the interface says so.
- **One roadmap per goal, no regeneration or versioning** at this milestone. `RoadmapService.generateRoadmap()` rejects a second call for the same goal (`RoadmapAlreadyExistsError`) rather than silently replacing or stacking roadmaps - the real AI integration is the natural point to revisit regeneration/versioning, not this one.
- **`completeActionStep()` is the only status-changing action**, deliberately not a generic status setter. Completing a milestone's last pending action step completes that milestone and activates the next one; completing the last milestone completes the roadmap - the same "expose only the transitions that are actually meaningful" pattern Goals' state machine already uses. It only accepts a step belonging to the roadmap's current *active* milestone (`RoadmapMilestoneNotActiveError` otherwise) - a step id is real and independently addressable, so without this check a caller could complete a step in a future milestone before the ones ahead of it, producing a state the UI never shows and the cascade logic doesn't anticipate.
- **Dashboard gains a real Roadmap dependency**, closing part of the gap ADR 0011 documented (Blueprint §10 formally lists Goals, Roadmap, Check-ins, Progress; only Goals existed). `DashboardService` now takes a `RoadmapsView` alongside `GoalsView` (both satisfied structurally by the real services), and `computeNextAction()` gained a `continue_roadmap` tier - inserted between "review a stale active goal" and "suggest adding a new goal," reflecting Vision §1/§20's "consistency over adding more": finish a step in an existing plan before either reviving a stalled goal takes priority, or a new commitment is suggested.
- **Web integration is intentionally light.** Onboarding's `FirstGoalStep` generates a placeholder roadmap for the first goal immediately after it's recorded (best-effort - a generation failure doesn't strand onboarding, since the deterministic generator can only fail on an infrastructure error, not a content one). Dashboard shows the next pending step as its `NextAction` card and a compact per-goal roadmap panel (milestones + steps, "Mark done" only on the currently active milestone). No dedicated Roadmap screen, no roadmap generation UI for goals outside onboarding - both are natural next steps once real AI-generated content makes a fuller view worth building.

## Consequences

- Every subsequent AI integration point in this project (Roadmap today; adaptive recommendations, coach summaries, etc. later) should follow this same shape: a narrow adapter interface returning a draft, a validation boundary the app enforces itself, and the app - never the generator - owning persistence and mutation.
- Verified with unit tests (`roadmapValidation`, `RoadmapService`, `PlaceholderRoadmapGenerator`, `FileRoadmapRepository`, updated `computeNextAction`/`DashboardService` tests), a domain-level integration test (`tests/integration/roadmap.integration.test.ts`), full-server HTTP tests for the new `/api/v1/roadmaps` and `/api/v1/goals/:id/roadmap` routes, and a real end-to-end browser run (Playwright against the live `apps/api`/`apps/web` dev servers) covering signup → onboarding → first goal → dashboard showing `continue_roadmap` and the roadmap panel → marking a step done → the next action advancing to the following step.
- Real database migration, roadmap regeneration/versioning, and any actual AI provider integration all remain open, same as every other adapter swap this project has deferred (ADR 0001).
