# ADR 0018: Cloud dev/preview environment planning (Vercel + Render)

**Status:** Accepted

## Context

Local release readiness (ADR 0017) made a fresh clone runnable end to end, but running Better You still depended entirely on someone's own laptop - there was no way to share a working instance with a collaborator. The user's next-milestone framing was explicit: "Cloud Dev / Preview planning, not production yet," specifically as *planning/readiness*, not a claim that deployment is solved. Two rounds of scoping happened before implementation: an initial broad "which hosting platform" framing was superseded once the user reported they'd already used Vercel (web) and Render (API) for a prior deploy attempt - at that point the open question changed from "which platform" to "how do we use the platforms already chosen, correctly and honestly."

## Decision

- **Hosting split: `apps/web` → Vercel, `apps/api` → Render.** Not re-litigated - already the user's own choice from prior hands-on use, and a reasonable one: Vercel suits a static Vite build with zero server to manage; Render suits `apps/api`'s real requirement (a conventional long-running Node process - Express, in-memory sessions, a real filesystem) that doesn't fit a serverless-functions platform without genuine rework.
- **`docs/environments.md`** documents three environments (local, cloud dev/preview, beta/shared testing) in one place, rather than scattering environment-specific instructions across multiple files - mirroring `RUNNING.md`'s own successful shape (one guide, one verification checklist) for local. Beta/shared testing is documented as *not started*, formally blocked on a hosted database adapter.
- **Render config specified precisely, not just "deploy apps/api"**: Root Directory `.` (repo root, not `Apps/api` alone) with Build Command `npm install` / Start Command `npm run start -w apps/api` - chosen specifically to reuse the exact install/module-resolution path already proven locally, rather than trusting a standalone install inside `Apps/api` to replicate workspace-hoisted behavior (`@types/node` is only declared as a root devDependency) correctly.
- **A real, verified gotcha documented, not glossed over**: Render injects its own `PORT` env var (default `10000`) and expects the server bound to it; `apps/api` reads `API_PORT`, not `PORT`. Confirmed against Render's current docs (not assumed from memory) that Render lets you override its own `PORT` value per-service, so the fix is setting both `PORT` and `API_PORT` to the same explicit value in Render's dashboard - no code change needed, but easy to miss without documenting it.
- **The persistence problem is stated as unresolved, with real numbers, not hand-waved.** Verified against Render's current docs while writing this: free web services cannot attach a persistent disk at all (paid-only), spin down after 15 minutes of inactivity, and the minimum paid tier supporting a disk is Render's Starter plan ($7/month) plus $0.25/GB/month for the disk itself. `docs/environments.md` presents the two honest options (pay for a disk, or accept resets) and explicitly does not pick one - matching the user's own instruction not to pretend deployment is solved.
- **A known, unfixed gap flagged rather than silently accepted**: the current `apps/api` CORS config (`cors({ origin: getEnv('API_CORS_ORIGIN', ...) })`) only accepts one static origin, which breaks Vercel's per-PR Preview Deployments (a fresh URL per branch). Documented as a real limitation - "one stable Vercel production deployment paired with one stable Render service" is the supported shape for now, not a redesign made as part of this planning-only milestone.
- **No secrets committed.** Every environment variable in `docs/environments.md` is documented by name and purpose only; real values belong in Vercel/Render's own dashboards, matching the existing local `.env` convention (ADR 0017).
- **No code changes made.** This milestone is documentation only - no `vercel.json`, no `render.yaml`, no CORS-origin-list change, no compiled build step for `apps/api`. Every one of those is named as a follow-up, not built speculatively ahead of an actual deploy.

## Consequences

- A collaborator with access to the user's own Render/Vercel accounts can follow `docs/environments.md` to stand up a real shared preview - but this session had no access to those accounts, so none of the Render/Vercel-specific settings above were verified against a live deployment. They're grounded in (a) direct inspection of this repo's actual `package.json`/`tsconfig.json`/`vite.config.ts` configuration and (b) current Render/Vercel documentation checked live while writing this - not guessed from possibly-stale memory - but the deployment-readiness checklist in `docs/environments.md` exists specifically because "documented" and "verified against the real platform" are still two different things, consistent with this project's standing rule against claiming something works without having actually run it.
- The persistence decision (pay for a Render disk vs. accept resets) is explicitly left open for the user to make, not defaulted - it's a real recurring cost commitment, not an implementation detail.
- The next concrete milestone this ADR points toward is a hosted database adapter (a new `*Repository` implementation behind the same interfaces every domain already depends on, per ADR 0001) - named as the right next step before serious beta testing, not started here.
