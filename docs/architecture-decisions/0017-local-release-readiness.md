# ADR 0017: Local release readiness - env loading, reset script, docs

**Status:** Accepted

## Context

Every domain through Progress was real and durable (ADR 0016), but actually running the project locally still required tribal knowledge: `.env.example` only documented one dead variable (`DEV_USER_ID`, left over from before Auth existed), nothing loaded `.env` automatically for `apps/api` (env vars had to be exported manually in the shell), `apps/web` had no `.env.example` of its own despite reading `VITE_API_BASE_URL`, both `README.md`s at the app level were stale (one still said "apps/web is not wired to this yet," the other still described the app as "Goal Creation Core"), and there was no way to reset local data short of manually finding and deleting `Apps/api/data/`. The user asked for the next milestone to be local release readiness - explicitly scoped to local/dev only, no production deployment - covering an env example, run docs, reset-data instructions, and a verification checklist.

## Decision

- **`.env` loading via Node's native `--env-file-if-exists` flag, not a `dotenv` dependency.** `apps/api`'s `dev`/`start` scripts became `tsx watch --env-file-if-exists=../../.env src/index.ts` / `tsx --env-file-if-exists=../../.env src/index.ts`. Verified directly that `tsx` (v4.23, built on Node 22) forwards this flag through to Node correctly, including under `tsx watch`. `--env-file-if-exists` (not `--env-file`) specifically so a missing `.env` isn't a startup error - every variable already has a working default (matching the pattern `getEnv()` already established). Requires Node 20.12+ (recorded as `engines.node` in the root `package.json`); `apps/web` needs no equivalent change since Vite already auto-loads its own app-level `.env` and exposes only `VITE_`-prefixed variables to browser code.
- **Two separate `.env.example` files, not one.** The root one (`API_PORT`, `API_CORS_ORIGIN`, `DATA_DIR`, and `DEV_USER_ID` - now explicitly labeled legacy/test-only, since Auth replaced the stub user in the running app back in the 2026-08-16 session) is consumed by `apps/api` via the flag above. `Apps/web/.env.example` (`VITE_API_BASE_URL`) is new, matching Vite's own convention of loading `.env` from the app's own directory, not the repo root. Both resolve to files already covered by the existing bare `.env` `.gitignore` rule (confirmed with `git check-ignore`) - no `.gitignore` change needed.
- **A real `reset-data` script (`scripts/reset-data.mjs`), not just prose instructions.** Deletes `DATA_DIR` (respecting a custom value from `.env`, resolved the same way `apps/api/src/index.ts` resolves it - relative to `apps/api`'s own working directory, not the repo root), refuses to run if the resolved path isn't clearly nested inside the repo (guards a misconfigured `DATA_DIR` like `.` or `..` from becoming an unintended `rm -rf`), and reports what it deleted. Built on `node:fs` only, no new dependency - the same "use what's already there" reasoning `packages/persistence` used for `readJsonArray`/`writeJsonArrayAtomic`. Wired as `npm run reset-data` (`node --env-file-if-exists=.env scripts/reset-data.mjs`, so a custom `DATA_DIR` is respected).
- **A new root `RUNNING.md`** as the single source of truth for local setup: prerequisites, install, environment setup, running both apps, a first-run walkthrough of what a fresh install actually looks like, an explanation of what does/doesn't survive a restart (data yes, sessions no - ADR 0016's own scoping), reset instructions, a literal verification checklist, and a troubleshooting section pulling forward two already-known gotchas from the development journal (stale long-running Vite dev servers, Windows port-killing via `netstat`/`taskkill`). `README.md`, `Apps/api/README.md`, and `Apps/web/README.md` were updated for accuracy (both app READMEs had gone stale relative to the real, current app) and now point to `RUNNING.md` for the full guide rather than duplicating it.
- **A `verify` npm script** (`typecheck && test`) added as the first line of the verification checklist - a single command to confirm the codebase itself is sound before manually walking through the app.
- **Explicitly local/dev only.** No Dockerfile, no build/deploy pipeline, no production env-var story, no database migration - none of that was in scope, matching the user's explicit framing. `RUNNING.md`'s own opening paragraph states this directly so it can't be mistaken for deployment guidance later.

## Consequences

- No domain service, route, or contract changed - this is entirely tooling and documentation, the same "adapter/infrastructure only" shape as ADR 0016.
- Verified live, not just written: copied both `.env.example` files to real `.env` files, ran `npm run dev:api` (confirmed it picked up the flag and started correctly), signed up a real account and created a real goal through the running API, hard-killed the process (`taskkill`, mirroring ADR 0016's own verification method), restarted it, and confirmed via a fresh login that the account and goal both survived. Then ran `npm run reset-data` and confirmed the data directory was deleted and reported correctly. Test artifacts (the account, the temporary `.env` files) were cleaned up afterward - `RUNNING.md` itself is what a real user follows from a clean clone, not something this session needed to leave running.
- Production deployment (hosting, a real database, HTTPS, a managed auth/email provider, secrets management beyond a local `.env`) remains fully open, consistent with every other explicitly-deferred piece in this project (the AI Roadmap Engine chief among them) - this milestone makes local development easy, not release-to-real-users ready.
- `DEV_USER_ID`/`getStubUserId()` itself was left in place, not deleted - it's still exercised directly by `tests/integration/goals.integration.test.ts`, and removing dead-but-tested code wasn't part of this milestone's scope. `.env.example` now says plainly that it doesn't affect the running app, closing the honesty gap where a developer copying `.env.example` might have assumed it configured real identity.
